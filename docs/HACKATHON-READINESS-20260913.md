# 看山任意门｜参赛契合与交付缺口

更新：2026-09-13。依据为用户补充的完整赛事说明与[官方 Skill 0.7.2 下载包](https://developer-cdn.zhihu.com/zhihu-cli/releases/beta/skill/0.7.2-beta.20260911131715/zhihu-cli-skill-0.7.2-beta.20260911131715.zip)，以及本轮实际代码/测试。当前产品方案见 [PRD v2.1](../PRD-v2.1.md)，验证记录见 [开发交付](DEVELOPMENT-20260913.md)。

## 判断

**方向符合「跨次元游乐场」，但尚未达到可直接交件的完成度。**

小说互动改编、角色扮演、AI NPC 和推理解谜均被规则明确鼓励。玩法库让不同故事有不同的操作，异步互助把知乎内容和人与人的联系同时带进游戏，社区价值较容易在体验中呈现。能否产生持续游玩/分享仍需玩家测试，不用“必然裂变”作为计划书结论。

已落实的基础是两部官方节选的章节试玩、公用动作与资源规则、分支校验和真实模型联调。当前不是完整的多人产品，也不是自动把所有小说编成高质量游戏的平台。

## 按评分安排开发

初审权重：AI 场景价值 40%、创新 25%、完成度 25%、体验 10%。决赛为 35%、25%、25%、8%，另有计划书与演示 7%。

- 场景价值：展示读者实际作决定、受到另一名玩家有限帮助的过程，以及原作来源。不要仅展示 LLM 长文本输出。
- 创新：让两种不同玩法和一次真实异步互助可操作，比宣称“任意小说全自动”更可验证。
- 完成度：先确保进入、行动、后果、结果、刷新、重玩完整；网络异常不让用户困在对话框。
- 体验：操作成本与锁定原因清楚，短时间能读懂目标，不靠工程术语理解产品。

## 接下来开发顺序

1. 在《近视眼》加入一个真实的匿名异步帮助：已完成清理 → 自愿留下方法 → B 采用后少消耗 1 体力 → A 收到使用回执。先补服务器回放和持久化存储，不直接信任 localStorage。
2. 做双会话、重复领取、旧版本、错误进度、无帮助、断网验收。帮助不能替玩家完成关键照料。
3. 确定公网宿主并验收 HTTPS、API、静态文件、额度、错误路径；不因 OAuth 推荐项阻塞基础 Demo。
4. 若拿到应用凭证且身份映射核实，接用户主动授权的关注关系排序；资料不足时保持真实匿名帮助。
5. 完成计划书和 3 分钟演示。留出干净浏览器与非开发设备验收时间，再锁定提交材料。

不要为了人气加入自动私信或强制拉人。创建项目、提交作品、向他人发送消息仍由用户明确指示后执行；当前没有做这些外部操作。
